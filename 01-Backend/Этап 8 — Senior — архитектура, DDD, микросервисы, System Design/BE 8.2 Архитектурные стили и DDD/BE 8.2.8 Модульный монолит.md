## Объяснение

Один процесс и деплой, но код разделён на **модули с чёткими границами**, которые соответствуют bounded contexts.

| Свойство | Требование |
|---|---|
| Границы | модуль = отдельные проекты/сборки, публичный контракт (интерфейсы/события), всё остальное `internal` |
| Данные | у каждого модуля своя схема/таблицы; нет `JOIN` между модулями и общих таблиц |
| Взаимодействие | через публичные API модулей или доменные события (in-process bus) |
| Зависимости | без циклов; проверяются архитектурными тестами |
| Команды | модуль принадлежит команде |
| Эволюция | модуль можно вынести в сервис, заменив вызовы на сетевые |

```text
src/
  Modules/
    Orders/       Orders.Contracts  Orders.Core  Orders.Infrastructure
    Billing/      Billing.Contracts Billing.Core Billing.Infrastructure
    Catalog/      ...
  Host/           # композиция модулей, единый процесс
```

```csharp
public interface IBillingModule { Task<InvoiceId> CreateInvoiceAsync(OrderId id, Money total, CancellationToken ct); }   // публичный контракт
builder.Services.AddOrdersModule(cfg).AddBillingModule(cfg);
```

Плюсы перед микросервисами: простота эксплуатации и транзакций, ниже задержка, легче рефакторинг. Плюсы перед «большим комом»: границы и независимость.

## Нюансы и подводные камни

- Без дисциплины (общая БД, прямые ссылки на внутренние типы) модули сливаются обратно в ком.
- Общий код `Common` разрастается в новый монолит внутри монолита.
- Транзакции между модулями появляются «случайно»: используйте события и eventual consistency, если планируете вынос.
- Один релиз для всех модулей: тесты и зависимость релизов.

## Практика

1. Разделите проект на 2–3 модуля с контрактами и `internal` реализацией.
2. Добавьте архитектурный тест на запрет ссылок на внутренности модулей.
3. Разведите схемы БД по модулям.

## Вопросы с ответами

> [!question]- Зачем модульный монолит?
> Даёт преимущества разделения по границам без сложности распределённой системы; путь к микросервисам при необходимости.

> [!question]- Как не допустить деградации в «ком»?
> Публичные контракты, `internal`, раздельные схемы данных и автоматические проверки зависимостей.
