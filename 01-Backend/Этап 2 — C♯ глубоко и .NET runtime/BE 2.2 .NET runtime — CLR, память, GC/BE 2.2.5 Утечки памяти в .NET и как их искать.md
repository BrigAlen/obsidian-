## Объяснение

### Что такое «утечка» в управляемой среде
GC освобождает объекты, до которых **нельзя дойти** от корней. Утечка в .NET — это когда объект остаётся достижимым (кто-то держит на него ссылку), хотя логически он больше не нужен. Плюс утечки неуправляемых ресурсов (дескрипторы, нативная память), которые GC не видит.

### Типичные причины
1. **События без отписки.** Долгоживущий источник держит делегат на короткоживущего подписчика.
```csharp
_settings.Changed += OnChanged;      // singleton держит this; без -= объект не соберётся
```
2. **Статические поля и синглтоны с накоплением.** `static List<T>`, `static Dictionary`, кэш без ограничения размера и срока жизни.
```csharp
private static readonly Dictionary<Guid, Report> Cache = new();   // растёт бесконечно
```
3. **Замыкания и захват `this`.** Лямбда в долгоживущем объекте удерживает весь контекст.
4. **Неосвобождённые `IDisposable`.** Соединения, потоки, `HttpResponseMessage`, `CancellationTokenSource`, таймеры.
5. **Таймеры и фоновые задачи**, которые не остановлены и держат ссылки.
6. **`HttpClient` в цикле** (`new HttpClient()` на запрос): сокеты и хэндлеры накапливаются.
7. **Scoped-сервис, внедрённый в Singleton** (captive dependency): scope-объект живёт вечно.
8. **Большие объекты в LOH** и фрагментация (не совсем утечка, но выглядит так).
9. **Нативные утечки**: P/Invoke, неуправляемая память, `Marshal.AllocHGlobal` без `Free`, библиотеки с нативными кэшами.
10. **ThreadStatic/AsyncLocal** данные, переживающие запрос.

### Признаки
- Память растёт линейно при постоянной нагрузке и не возвращается после её снижения.
- Растёт `gen2 size` и количество Gen 2 сборок, `time in GC`.
- Контейнер перезапускается (OOMKilled, код 137).
- В Kubernetes: рост `container_memory_working_set_bytes` без плато.

### Как искать
1. **Метрики.** `dotnet-counters monitor -p <pid> System.Runtime` (gc-heap-size, gen-2-size, loh-size, alloc-rate, exception count).
2. **Снимки кучи.** Сделать два-три снимка с интервалом и сравнить.
```bash
dotnet-gcdump collect -p <pid> -o before.gcdump
# нагрузка, ожидание
dotnet-gcdump collect -p <pid> -o after.gcdump
# открыть в Visual Studio / PerfView, сравнить: какие типы растут
```
3. **Полный дамп** для анализа корней: `dotnet-dump collect -p <pid>`, затем `dotnet-dump analyze` (`dumpheap -stat`, `gcroot <адрес>` покажет цепочку ссылок от корня до объекта).
4. **Профайлеры**: dotMemory, Visual Studio Diagnostic Tools, PerfView, Rider.
5. **Локальное воспроизведение**: нагрузочный тест (k6, NBomber) + `GC.GetTotalMemory(forceFullCollection: true)` до/после.

```bash
dotnet-dump analyze core_dump
> dumpheap -stat            # какие типы занимают память
> dumpheap -type Patient    # адреса объектов
> gcroot 0x00007f...        # кто держит объект
```

### Как чинить и предотвращать
- Отписываться от событий (`Dispose`, `-=`), использовать слабые события или `IProgress<T>`/Channels.
- Ограничивать кэши: `MemoryCache` с `SizeLimit`, `AbsoluteExpiration`; `HybridCache`.
- Освобождать ресурсы через `using`/`await using`; `IHttpClientFactory`.
- Проверять время жизни зависимостей в DI: `ValidateScopes`/`ValidateOnBuild`.
- Не хранить в статике данные, растущие с числом запросов.
- Метрики памяти и алерты на рост в мониторинге (Grafana), лимиты контейнера.

## Нюансы и подводные камни
- «Память выросла» не всегда утечка: GC не спешит возвращать память ОС, а Server GC резервирует много. Сравнивайте размер кучи после `GC.Collect` в тестовой среде, а не RSS.
- Снимок кучи без нагрузки между замерами бесполезен: нужна разница.
- Утечки в нативных библиотеках не видны в `gcdump`: смотрите RSS против размера управляемой кучи.
- Не вызывайте `GC.Collect()` в проде, чтобы «скрыть» утечку.
- Тестируйте утечки долго: медленная утечка проявится через часы.

## Практика
- Воспроизвести утечку через статическое событие и найти её в `dotnet-gcdump` (сравнить два снимка).
- Показать через `gcroot`, кто держит подписчика.
- Ограничить `MemoryCache` по размеру и проверить, что память выходит на плато.

## Вопросы с ответами
> [!question]- Как может быть утечка памяти, если в .NET есть GC?
> GC освобождает только недостижимые объекты. Если на объект остаётся ссылка (событие, статическое поле, кэш, замыкание), он не будет собран. Кроме того, GC не управляет неуправляемыми ресурсами.

> [!question]- Назовите частые причины утечек.
> Подписки на события без отписки, статические коллекции и неограниченные кэши, неосвобождённые IDisposable, захват `this` в долгоживущих лямбдах, scoped-сервисы в синглтонах, нативные ресурсы.

> [!question]- Как вы будете искать утечку в продакшене?
> Смотрю метрики (`dotnet-counters`, рост gen2/LOH), снимаю два `dotnet-gcdump` с нагрузкой между ними и сравниваю типы, при необходимости снимаю полный дамп и через `gcroot` нахожу корень, который держит объекты.

> [!question]- Что показывает `gcroot`?
> Цепочку ссылок от корня GC (статическое поле, стек, handle) до конкретного объекта — то есть почему объект не собирается.

> [!question]- Как отличить утечку от нормального поведения GC?
> После снижения нагрузки и полной сборки размер управляемой кучи должен падать. Если он остаётся высоким и растёт от цикла к циклу — утечка. Рост RSS при стабильной куче может быть нативной утечкой или поведением Server GC.
